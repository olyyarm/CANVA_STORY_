# AssetStore: первый этап рефакторинга

## Зачем нужен отдельный контракт ассетов

Изображения, аудио и видео больше не должны зависеть от временного `blob:` URL. Нода хранит стабильную ссылку `AssetReference`, а конкретное хранилище отвечает за сохранение файла и восстановление URL для интерфейса.

Этот этап не меняет пользовательский сценарий и не начинает отдельную систему видеоманхвы. Он закрепляет совместимую основу, на которую позже можно опереть карточки персонажей, библиотеку локаций, эпизоды, сцены, production-статусы, изображения и motion-промпты.

## Стабильный контракт

`AssetReference` разделяет три разных понятия:

- `mediaKind` — физический тип данных: `image`, `audio` или `video`;
- `assetKind` — назначение: референс персонажа, локация, кадр сцены, системная вставка, фон главы, озвучка, клип сцены или собранное видео главы;
- `scope` — область принадлежности: проект, глава, сцена, персонаж или локация.

Дополнительные поля связывают ассет с проектом и будущими реестрами:

- `projectId`, `chapterId`, `sceneId`;
- `canonicalId` для постоянной сущности, например персонажа или локации;
- `sourcePrompt` для воспроизводимости генерации;
- `filePath` для будущего файлового хранилища;
- `mimeType`, `createdAt`, `updatedAt`.

`storage` сейчас имеет значение `indexeddb`. Значение `file` зарезервировано для будущего адаптера папки проекта и не означает, что браузер уже умеет записывать произвольные локальные файлы.

## Текущий жизненный цикл

1. Генератор возвращает URL или `Blob`.
2. `assetStorage.ts` сохраняет бинарные данные в IndexedDB.
3. В ноде сохраняется `AssetReference`; временный URL не считается частью документа проекта.
4. Автосохранение записывает структуру нод и ссылки в `localStorage`.
5. После перезагрузки приложение читает бинарные данные по `assetId` и создаёт новый объектный URL.

Старые документы остаются совместимыми. При импорте `project.ts` проверяет новый контракт и, если его ещё нет, собирает ссылку из прежних полей `localAssetId`, `localAudioAssetId` и `localVideoAssetId`.

## Граница обычного JSON-экспорта

JSON содержит описание проекта и `AssetReference`, но не бинарные данные IndexedDB. Поэтому он подходит для резервной копии структуры и обмена проектом без тяжёлых файлов. Для полноценного переноса между компьютерами нужен проектный пакет, например ZIP с JSON и каталогом `assets`.

## Следующие небольшие этапы

Восстановление и автосохранение медиа уже вынесены из `App.tsx` в `useAssetPersistence`. Хук использует `saveAssetFromUrl` и записывает семантическую ссылку рядом с прежними metadata-полями, поэтому старые документы продолжают работать.

Следующие шаги:

1. Добавить адаптер папки проекта и переносимый экспорт/импорт с бинарными файлами.
2. По очереди вынести из `useNodeManagement.ts` генераторы текста, изображений и аудио. Браузерная сборка видео уже находится в `services/videoGeneration.ts`.
3. Отдельно вынести оркестрацию таймлайна и реестры персонажей/локаций, не меняя старые ноды.

Каждый этап должен оставлять старые ноды рабочими и завершаться lint, production build и проверкой сохранения после перезагрузки.
